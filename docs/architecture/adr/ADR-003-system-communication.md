# ADR-003: 系统间通信模式 — 直接调用 + 接口契约

| 字段 | 值 |
|---|---|
| ADR 编号 | 003 |
| 标题 | 事件总线 vs 直接调用 vs 共享状态 |
| 状态 | ACCEPTED |
| 日期 | 2025-07-14 |
| 决策者 | 程基岩（技术主程） |
| 关联文档 | `main-architecture.md` §3、`design/gdd/system-decomposition.md` |

## 上下文

本项目有 6 个核心系统（C1-C6）需要相互通信：

- C1（叙事引擎）需要驱动 C3（选择系统）、C5（存在保护）、C2（天使系统）。
- C3（选择系统）处理选择后需要通知 C4（Sephirot 进程）、C2（天使响应）、C5（存在保护触发）。
- C5（存在保护）触发暗流后需要调用 C2（天使介入）。
- C4（Sephirot 进程）完成质点后需要通知 C2（翅膀阶段更新）。
- C2（天使系统）的状态需要被 C3（选项过滤）、C1（呈现）读取。

通信特点：
1. **调用链明确**：大多数交互是"A 做了 X，通知 B 处理 Y"的确定性流程，不是松散的事件广播。
2. **状态一致性要求高**：多个系统读写共享变量（见主架构 §4.4 所有权矩阵），需要明确的写入权威。
3. **调用频率低**：叙事驱动，每分钟可能只有几次系统间调用（非实时高频通信）。
4. **调用顺序重要**：选择处理需要先更新 C3 状态，再通知 C4，再更新 C2，顺序不能乱。
5. **可调试性重要**：叙事游戏出 bug 时需要追踪完整的调用链。

## 备选方案

### 方案 A：事件总线（Event Bus / Pub-Sub）

**概述**：系统通过事件总线发布和订阅事件，彼此不直接引用。

**优势**：
- 松耦合：系统间无直接引用，增删订阅者不影响其他系统。
- 可扩展：新系统可订阅已有事件，无需修改发布者。
- 适合广播场景：一个事件多个消费者。

**劣势**：
- **调用顺序不可控**：多个订阅者的执行顺序不确定，但本项目的选择处理需要严格顺序（C3→C4→C2）。
- **调试困难**：事件链路隐式，出 bug 时难以追踪完整调用路径。
- **状态一致性风险**：事件驱动的状态修改分散在多个订阅者中，难以保证共享变量的单一写入权威。
- **过度设计**：本项目只有 6 个系统，通信路径有限且明确，事件总线的松耦合优势无法发挥。
- **错误处理复杂**：某个订阅者抛异常，影响其他订阅者的执行。

### 方案 B：直接调用 + 接口契约

**概述**：系统之间通过明确定义的接口方法直接调用，调用关系显式可见。

**优势**：
- **调用顺序明确**：代码中调用顺序即执行顺序，可读性强。
- **调试简单**：调用栈直接反映调用链，断点即可追踪。
- **状态一致性可控**：共享变量的写入权威明确在接口契约中定义。
- **错误处理直接**：try-except 可精确控制在哪个调用点处理错误。
- **代码即文档**：调用关系在代码中显式可见，无需额外文档描述事件流。
- **适合确定性流程**：本项目的系统交互大多是确定性流程（选择→处理→更新），非松散事件。

**劣势**：
- 系统间有直接引用，耦合度较高。
- 新增系统交互需要修改调用者代码。
- 不适合真正的广播场景（但本项目几乎不需要广播）。

### 方案 C：共享状态（全局变量/单例）

**概述**：所有系统共享一个全局状态对象，各系统直接读写状态字段。

**优势**：
- 实现简单，无需接口定义。
- 数据访问直接，无调用开销。

**劣势**：
- **状态一致性灾难**：任何系统可修改任何变量，写入权威无法保证。
- **调试极困难**：无法追踪谁在什么时候修改了什么变量。
- **强耦合**：所有系统依赖全局状态结构，修改一个字段影响所有系统。
- **不可测试**：系统无法独立测试（依赖全局状态）。
- **不可扩展**：状态结构膨胀后管理困难。

## 决策

**选择方案 B：直接调用 + 接口契约。**

### 决策理由

1. **调用顺序是硬需求**：选择处理的调用链（C3 更新 → C4 进程 → C2 天使响应 → C5 存在保护）有严格的顺序依赖。事件总线无法保证顺序；直接调用天然保证顺序。

2. **共享变量所有权是核心约束**：Phase 2 的两个 CONCERN 本质上都是状态一致性问题。直接调用 + 接口契约模式使得每个共享变量的写入权威（所有者）在接口定义中明确——只有所有者暴露的 setter 才能修改变量。

3. **可调试性优先**：叙事游戏的 bug 通常是"某个选择后状态不对"，需要追踪完整调用链。直接调用的调用栈直接反映调用链；事件总线需要额外的事件追踪工具。

4. **通信路径有限且明确**：6 个系统之间的通信路径约 10-15 条，全部在主架构 §3.4 中明确定义。

5. **项目规模不需要松耦合**：事件总线的松耦合优势在系统数量多（10+）、通信路径复杂（50+）、频繁增删系统时才能体现。本项目 6 个系统的固定通信路径，直接调用足够。

### 混合策略

虽然主体选择直接调用，但在以下场景使用轻量事件机制：

| 场景 | 机制 | 理由 |
|---|---|---|
| 系统状态变化通知 UI | Ren'Py Screen 的 `on` 语句 / 属性绑定 | UI 是被动消费者，不需要调用接口 |
| 成就解锁通知 | `persistent.achievements` 直接写入 + Screen 检测 | 成就是跨周目持久数据，不需要实时通知 |
| 存档触发 | C6 暴露 `save_game()` 接口，C1/C4 直接调用 | 存档是确定性操作，不需要事件 |

## 后果

### 正面后果

- 调用链清晰可追踪，调试成本低。
- 共享变量写入权威在接口契约中强制执行（违反者在 code review 中标记为 BLOCKER）。
- 系统可独立测试（mock 接口即可隔离系统）。
- 代码即文档，调用关系无需额外维护。

### 负面后果

- 系统间有直接引用，新增系统交互需修改调用者。
- 需要维护接口契约文档（主架构 §3.4 已包含）。
- 系统实例化顺序有依赖（需要先实例化被依赖的系统）。

### 风险缓解

| 风险 | 缓解措施 |
|---|---|
| 系统间循环依赖 | 定义依赖方向：C1→C3→C4, C1→C5→C2, C3→C2, C3→C5；禁止反向依赖 |
| 实例化顺序问题 | 使用统一的系统初始化函数，按依赖顺序实例化 |
| 接口变更影响范围 | 接口变更需要更新主架构 §3.4 和对应 ADR |
| 接口膨胀 | 每个系统暴露的接口不超过 8 个方法；超出时考虑拆分系统 |

## 系统依赖方向图

```
C1 叙事引擎
  ├──→ C2 天使系统（调用 angel_intervene, update_wing_stage）
  ├──→ C3 选择系统（调用 present_choices）
  ├──→ C5 存在保护（调用 trigger_undertow, recover_temporary_dim）
  └──→ C6 存档（调用 save_game）

C3 选择系统
  ├──→ C2 天使系统（调用 update_angel_response, update_emotional_state, add_bond_depth）
  ├──→ C4 Sephirot系统（调用 process_confrontation）
  ├──→ C5 存在保护（调用 trigger_undertow，通过 existence_protection_trigger）
  └──→ C1 叙事引擎（返回 narrative_jump）

C5 存在保护
  └──→ C2 天使系统（调用 angel_intervene）

C4 Sephirot系统
  └──→ C2 天使系统（调用 update_wing_stage, add_bond_depth for Ch13）

禁止的依赖方向：
  ✗ C2 → C3（天使系统不调用选择系统）
  ✗ C2 → C4（天使系统不调用 Sephirot 系统）
  ✗ C4 → C3（Sephirot 系统不调用选择系统）
  ✗ C4 → C5（Sephirot 系统不调用存在保护系统）
  ✗ C5 → C3, C5 → C4（存在保护不调用选择/Sephirot 系统）
  ✗ C6 → 任何系统（存档系统是被动的）
```
